## Project purpose and shape

This repository is a JavaScript ES module browser game and app project with its own source generator, live development watcher, and Node backend. The game design document lives in the separate [sapmi-game repository](https://github.com/kristus123/sapmi-game). The browser currently mounts the Vikingheim `village-page` component from `frontend/index.js`; other apps in `frontend/apps/` are present and may be experimental or selectively enabled.

Keep changes in their owning source area:

- `frontend/` contains the browser app entry point, canvas/game engine primitives, UI and CSS, app experiments, and image/audio/Aseprite assets. `frontend/tools/game/` covers drawing, input, physics, positions, pathfinding, quests, and startup/assets. `frontend/tools/network/` and `frontend/tools/core/` cover networking, media, audio, device access, storage, and utilities. `frontend/apps/` holds app/game experiences such as canvas game, RPG/Sámi game, livestream, language practice, code editor, and baby games.
- `backend/` contains the HTTP server/routes/endpoints, WebSocket server, mediasoup SFU/RTC services, token helpers, and integrations.
- `shared/` contains code generated for and used by both browser and backend. Changes here can affect both runtimes.
- `dev/` contains the custom file watcher, generators, source transpiler, automatic import resolution, Aseprite conversion, and build helpers. Treat its assumptions as part of the project architecture.
- `scripts/` and `prod/` contain lint/build/deployment/maintenance utilities. Inspect a script before running it: some change files, contact external services, deploy, or act on a production server.
- `documentation/` contains coding, setup, Aseprite, Capacitor, and VPS notes. Several deployment notes are host-specific and should be treated as examples, not portable defaults.
- Root files such as `Paths.js`, `AllImports.js`, `watch.js`, and `start.js` are part of the build/runtime pipeline.

## Runtime and module architecture

The project has two related but different runtime paths:

- In development, `watch.js` writes the ignored `AllImports.js`, checks source filenames, clears `dist/`, and starts a polling watcher over `shared/`, `frontend/`, and `backend/`. The watcher polls every 50 ms and reacts only to `.js`, `.aseprite`, `.html`, `.css`, and `.md` changes. Changes are grouped with a 100 ms debounce. Once a change is detected, the watcher stops the backend, completes the required frontend, external bundle, Aseprite, and backend generation, then starts the backend with a new ID. Frontend-only changes skip backend generation; backend-only changes skip frontend and external bundle generation; shared changes rebuild both. The backend reports `ready: true` from `/ping` only after its HTTP, SFU, and WebSocket services are initialized. The browser waits for that signal before opening or reopening its WebSocket, then checks the backend ID and reloads if it changed. The initial build finishes frontend, Aseprite, external bundle, and backend generation before serving `dist/` on port `5050` and starting the backend on port `3000`.
- In production, `node dev/GenerateFrontend.js PRODUCTION` builds the static browser output and `node start.js PRODUCTION` generates and starts the backend. `start.js` does not start the static frontend server; production hosting/deployment is handled separately.

`watch.js` calls `Swoo.killPorts()` before startup. That runs `scripts/kill_ports.sh`, which force-kills processes listening on ports `3000` and `5050` when `lsof` is available. Account for that side effect before starting the watcher on a machine with services already using those ports.

Frontend startup is coordinated in `frontend/index.js`: it imports the enhancement runtime from `frontend/index.html`, registers all generated HTML components before initializing any `-page` records (page layouts may be registered later in the same parallel component pass), loads CSS, fonts, and catalogued image/audio/Aseprite assets, then mounts `hub-page`. The canvas game loop is in `frontend/CanvasLoop.js`; game systems under `frontend/tools/game/` provide input, camera, drawing layers, physics, positions, entities, quests, and sprite/asset loading. `frontend/ui/html/` builds DOM elements and `frontend/ui/page/` provides simple page switching. Other `frontend/apps/` modules are opt-in experiments/apps; they are not automatically launched by the entry point.

Hyphenated HTML templates are registered by `frontend/ui/html/RegisterCustomWebComponent.js`, which parses the template, imports the optional paired module, and defines the element class inline. Its `_initialize()` clones the template for each instance, wires state and attributes, exposes template fields, and stores `onDomAdd` and `onDomRemove`. Setup runs once. Supplied child nodes are preserved during asynchronous setup and projected into matching default or named `<slot>` placeholders; `slot-*` attributes can still provide text content. A single `_lifecyclePromise` queue serializes DOM hooks; reconnection waits for the previous removal hook. The public `whenReady()` method returns the setup promise after the component is connected; navigation can await setup without accessing private DOM hooks or their queue. `_setupPromise` keeps initialization to one run. The connection hook checks `isConnected` after asynchronous setup so detached components do not start DOM-bound work. `onDomAdd` runs after setup on each connection, and `onDomRemove` runs after pending setup and addition callbacks finish on each removal, including removal during setup. Both take no arguments. DOM removal preserves children, fields, state, and handlers. There are no destruction flags, recursive destruction, `onDestroy`, or `neverDestroy` options. Callers can hold ordinary components in variables and reattach them; JavaScript can reclaim detached elements when they are no longer referenced. Stop external timers and subscriptions in `onDomRemove` and restore them in `onDomAdd`.

Shared layout infrastructure lives in `frontend/ui/layout/Layout.js`; the Vikingheim `pretty-layout` component is under `frontend/apps/viking_game/layout/pretty-layout/`. Shared HTML infrastructure lives directly under `frontend/ui/html/`, while component-specific custom elements use subfolders such as `frontend/ui/html/custom/pop-over/`.

Page modules export `const page = { persistOnClose: true }` separately from their default setup function. After each custom element is registered, `frontend/index.js` calls `Page.init(tag, module.page)` for names ending in `-page`. Registration validates explicit boolean persistence, creates a detached persistent element, and leaves nonpersistent records with `page: null`. The generic component registrar does not reference navigation; it returns the loaded module so startup reuses its page metadata without a second import. Its setup promise resolves to the returned instance options; `Page.open()` stores the setup result in the record’s `options` field and reads `onPageOpen`, `onPageClose`, and `onToggle` from it, so callbacks can close over instance state. `Layout.init(name)` reuses one layout element per registered layout name, so pages using the same layout share its DOM and setup state while navigation moves the active page through that shared layout. Closing a nonpersistent page clears both `page` and `options`. Opening uses registered persistence to reuse the cached element or create a fresh nonpersistent instance. Setup errors propagate without cleanup. `Page.activeTag` holds the active name, while `Page.active` returns its record and throws when no page is active. Opening the active page or closing without an active page throws. Opening and closing return no element. Closing runs callbacks, removes the element, clears nonpersistent element references, and resets `activeTag`. Direct DOM changes invoke only component DOM hooks.

Layouts keep a comment marker in their default slot through `Layout.pageSlots`. `Layout.attach(name, page)` inserts each page before this marker, retaining the original content position after the component's one-time slot projection. Navigation between pages with the same layout keeps the layout connected and removes only the old page; do not append subsequent pages directly to the layout host or reconnect the layout. Leaving for another layout, a layout-free page, or calling `Page.close()` removes the layout while preserving its marker for reuse. `node --test dev/tests/PageChecks.js` covers sharing, page persistence, closing, and navigation between layouts.

Page hosts receive the `page-host` class and already fill their parent with `width: 100%` and `height: 100%`; the class also makes them flexible (`flex: 1`, with zero minimum dimensions) so a page slotted into a flex layout can occupy a constrained middle region without pushing out headers or footers.

`CustomElementHelper.exposeFields(element)` exposes template IDs and tag-name shortcuts before the paired module runs, then refreshes them after nested slot replacement. `CustomElementHelper.removeFields(element)` remains an available ID-field cleanup utility but is not called on DOM removal. The module's initial `state` can be a string or an asynchronous function returning a string; `CustomElementHelper.createSetState(element)` creates a callback which validates state and updates descendants' `show-if-state` visibility. Keep the original slot nodes during asynchronous setup so parent-supplied slots can replace placeholders rendered by nested components.

The custom source pipeline is important when changing JavaScript:

ARIA attributes and ARIA roles are not needed in this project; do not add them to UI markup.

- `dev/GenerateFrontend.js` copies `frontend/` into `dist/`, runs `dev/Transpiler.js`, concatenates all frontend CSS into `dist/swag.css`, and generates `AssetPaths.js` data from HTML/Markdown, images, audio, and Aseprite filenames. `dev/ExportAseprite.js` stores generated files under the ignored `.cache/aseprite/<basename>/`, regenerates them only when one of the expected cached outputs is missing or older than its source, then copies them to `dist/generatedAseprite/<basename>/`.
- Development/build utilities must not directly load frontend/backend source modules through the lazy-import index: parenthesis-free control flow is not valid Node syntax before transpilation. `GenerateFrontend` uses `node:crypto`'s `randomUUID()` for the service-worker cache ID rather than loading the browser random utility.
- `dev/Transpiler.js` is source rewriting, not just syntax transpilation. It infers imports by scanning identifiers, adds `SuperClass` inheritance to exported classes, rewrites constructor-style factory calls, inserts null checks and constructor parameter assignments, rewrites `if`/`switch`/`for` syntax, and substitutes `ENVIRONMENT`. Keep custom control-flow headers on one source line; the rewriters cannot parse multiline conditions such as an object-literal call inside the condition. Inspect the source and generated output when a change depends on any of those behaviors. Add `// no-null-check` to each function signature that intentionally accepts `null` or `undefined`; annotating a caller does not disable checks inserted in a nullable helper it calls. `// disable-transpiling` opts a JavaScript file out of those source transformations.
- Frontend and backend source use parenthesis-free `if condition {`, `else if condition {`, `switch value {`, and `for` headers (`for let i = 0; i < count; i++ {`, `for const item of items {`, `for const key in object {`, and `for await const chunk of stream {`). The transpiler restores JavaScript parentheses and wraps `if`/`else if` conditions with `IfCondition.validate()`. Loop headers must fit on one line and end with their opening `{`, optionally followed by a line comment; missing braces and multiline headers throw. Standard one-line loop headers are also accepted, and the converter/linter removes their outer parentheses. `Parameters.extractIfPresent()` must ignore these control-flow headers so calls inside a condition or loop are not mistaken for function declarations. Shared files and files marked `// disable-transpiling` use standard JavaScript control-flow syntax because they do not receive these rewrites.
- `node dev/ConvertControlFlowSyntax.js` converts standard one-line control-flow headers in frontend/backend source to the custom syntax. Its `--check` mode reports pending conversions without writing. It skips shared code and any file containing `// disable-transpiling`, and it only removes parentheses when they wrap the entire condition, preserving expression parentheses such as `(await camera).state`.
- `scripts/lint.sh` runs `dev/LintProject.js`. It uses `ConvertControlFlowSyntax` to present standard control-flow and case blocks to ESLint in memory, then restores custom source syntax before writing fixes. Temporary case breaks match the runtime's implicit breaks and are removed before writing. Shared files and `// disable-transpiling` files retain standard syntax.
- ESLint keeps array destructuring patterns on one line in frontend/backend source, so formatting a loop with three or more destructured values cannot create a multiline header that the transpiler rejects.
- `dev/GenerateBackend.js` copies `shared/` into `transpiledBackend/shared/`, substitutes the environment, and adds inferred imports to generated backend files. Backend JavaScript also passes through the shared transpiler transformations used by the frontend, including class inheritance/constructor handling, null checks, constructor-style factory rewrites, and `if`/`switch`/`for` rewrites. Shared source files receive environment substitution and inferred imports but are not otherwise transpiled.
- `frontend/index.html` supplies the `#root/` browser import map. `package.json` supplies the matching `#root/*` mapping for Node. `AllImports.js` is a separate generated lazy-import index; never edit it by hand.
- HTML/Markdown templates are collected by basename. Hyphenated HTML files are emitted as custom web components, with an optional same-basename JS module. CSS is concatenated rather than imported one stylesheet at a time.

Backend HTTP and WebSocket share the Node HTTP server on port `3000`. `backend/StartServer.js` enhances built-in prototypes, imports endpoint modules to register handlers on `AdminRoute`, `UserRoute`, or `UnsecureRoute`, starts `HttpServer`, starts mediasoup (`SfuServer`), and attaches `SocketServer` to the HTTP server. HTTP POST route names map to those handler registries; WebSocket messages dispatch by `action`. Coordinate client action/payload changes with `frontend/tools/network/`. The mediasoup signaling server is in `backend/rtc/`, with its client-side peer/router handling in `frontend/tools/network/multiplayer/rtc/`.

WebSocket messages use an envelope with `data` for the application payload and `metaHeaders` for message metadata. Clients pass the complete encoded token as the `token` query parameter when connecting; `SocketServer` validates it with `ShaToken.decode()` and derives the socket identity from the signed `internal.userId`. Use `originUserId`, `targetUserId`, and `targetUserIds` for message routing, and `userIds` in `UPDATE_USERS_LIST` payloads. The server derives sender identity from the authenticated socket rather than trusting client-supplied metadata. Multiple sockets for one user share a user ID and user-directed messages are delivered to each of that user's connected sockets.

`shared/` is built for both browser and backend, but each runtime initializes a different set of prototype enhancements: `frontend/index.html` loads `shared/enhance/EnhanceAll.js`, while `backend/StartServer.js` calls `EnhanceBackend()`. Put genuinely cross-runtime code in `shared/` and check that it uses APIs available in both environments.

## Main app areas

- `frontend/tools/game/`: canvas engine primitives and game systems. `frontend/apps/canvas_game/CanvasGame.js` is mounted in the AOE page's middle area; the Sámi RPG under `frontend/apps/rpg_sami_game/` remains an opt-in experience. The Sámi game's design document is maintained in the separate `sapmi-game` repository.
- `<offset-element>` is a reusable custom web component registered from `frontend/ui/html/custom/offset-element/offset-element.html` and configured by `frontend/ui/html/custom/offset-element/offset-element.js`. Its zero-height grid host fits its content up to the parent width in normal flow, and grows into available width when it is a flex item; optional `width` sets an exact horizontal footprint. `offset-x` and `offset-y` move the projected content without adding height to the parent. Styling lives beside the component in `frontend/ui/html/custom/offset-element/offset-element.css`.
- In `frontend/ui/css/attributes/flex.css`, `[place-top]` sets `align-items: flex-start`: on `flex-h` this aligns children to the top, while on `flex-v` it aligns them to the left. `flex-v` defaults to `justify-content: space-evenly`; add `[close]` when its children should start at the top of the column.
- `frontend/apps/viking_game/village/`: Vikingheim's `village-page` mounts the walk-around village canvas in its flexible middle area (`flex: 1; min-height: 0`) so the footer stays visible. The story `viking-page` and its `Advisors.js`/`Story.js` data live together under `frontend/apps/viking_game/viking-page/`. The large illustrated world map is `map-page` under `frontend/apps/viking_game/map/`; the footer switches between Village (`village-page`) and Map (`map-page`). `<offset-element>` places portraits above the footer without changing its height.
- `frontend/apps/livestream/`: browser recording/device-selection and stream UI; `SwappableMediaStream` sends one selected microphone through Web Audio before `MediaRecorder`. `Stream.setAudioDevice()` selects the active input, and `Stream.clearAudioDevice()` mutes it. The selection controls are in `ui/streamer/streamer-page.js`; radio inputs use the native `change` event because the `OnChange` enhancement only supports checkboxes. `backend/http/endpoints/hls/` accepts WebM chunks and uses FFmpeg to produce HLS output under ignored `public_folder/hls/`. `HlsVideo.connect()` reports startup failures through callbacks. `HlsJs` is a static wrapper: it owns the hls.js import, one engine, callbacks, `connect(video, source, callbacks)`/`disconnect()`, and `playingDate` access. Its error/manifest listeners are registered once. Disconnection and UTC access are safe when hls.js is unsupported or detached. It notifies `onManifestParsed`; `HlsVideo` calls the video element's `play()` method and handles playback failures. `H.hlsVideo()` accepts `reportPlaybackDate` and calls it on `loadeddata`, `timeupdate`, and `seeked`; the player reads UTC exclusively from `HlsJs.playbackUtc` (`hls.playingDate`) and notifies the viewer. Native HLS remains a playback fallback, but provides no UTC date; clipping requires a playback UTC date from hls.js. There is no native date calculation or separate playlist date polling. Media errors trigger a stream-status check before reconnecting or stopping playback. This flow is distinct from the mediasoup SFU used for live WebRTC calls/rooms.
- Livestream viewer arrows call `hlsVideo.video.seekBy()` for 30-second jumps. `getSeekTarget()` and `seekBy()` are video-element enhancements in `shared/enhance/html/Enhance_html_video.js`; they work with native and hls.js playback whenever seekable ranges exist. `getSeekTarget()` clamps to the video's `seekable` ranges, avoids gaps and the exact live edge, and returns `null` when movement is unavailable; the viewer uses this to disable buttons. Seeking updates the displayed playback UTC, including on `seeked`. `HlsVideo.playbackUtc` owns the current playback date used for clips and resets when playback stops or starts a connection.
- The viewer creates one `const hlsVideo` and keeps its video element attached. `HlsVideo.connect()` uses `Retry(5, ...)` for stream status and connection setup; healthy connections are a no-op. Its `connected` getter reads the hls.js media attachment or native video source, with no extra connection flags, signals, or `Listener` dependency. Playback errors notify the viewer, which disconnects and lets the next status check reconnect. The viewer uses `SetTimeoutLoop(4_000, async () => { ... }).stop()` for serial HTTP status checks, starts the loop on connection, and stops it with `HlsVideo.disconnect()` on disconnection. Offline streams resume automatically when status becomes online; failed status requests retain playback and retry on the next check. There is no stream-status socket protocol. `SetTimeoutLoop(delayMs, run)` starts automatically, queues the first callback in a microtask, and waits for each callback before scheduling the next timeout. Its chainable `start()` and `stop()` methods support reuse; stopping clears the pending timeout, and restarting during an active callback waits for it to finish before scheduling another run. Chaining `.stop()` during construction prevents the first callback from running until restarted. `Screen.toggleFullscreen()` owns fullscreen switching. Native HLS remains a playback fallback and provides no UTC date; accurate playback UTC requires hls.js-managed playback.
- `frontend/apps/practice_language/`, `frontend/apps/code_editor/`, and `frontend/apps/baby_game/`: standalone browser app experiments with their own template files. `frontend/apps/baby_game/` includes small game prototypes and local image/audio assets. Hub cards open `find-pair-page` with `Page.open()`, and its top-left button returns to `hub-page`. The game uses `persistOnClose: false` to start fresh on replay. Hub cards need no lifecycle opt-out: ordinary components keep their contents when disconnected, so the cached hub retains its nested controls and state.
- `frontend/tools/core/`: audio, browser device/media access, IndexedDB, and worker helpers. `frontend/tools/network/`: HTTP/token/persisted-data helpers, WebSocket multiplayer, lobby utilities, and RTC clients.

## Generated and local-only files

`dist/` is generated browser output and `transpiledBackend/` is generated backend output; both are ignored by Git. Do not hand-edit them. Change source under `frontend/`, `shared/`, or `backend/`, then regenerate through the appropriate workflow. `AllImports.js` is generated at watcher startup from named exports. Do not edit it manually; duplicate exported names across modules make generation fail.

`Secrets.js` is gitignored local configuration. Never print, copy, or commit its contents. Keep credentials, tokens, private keys, and machine-specific paths out of tracked files and documentation. Keep local secrets out of shared source and browser output. `ServerConfig.shaSecret` currently uses `CHANGE_ME` in development and the placeholder `TODO_FIX_LATER` in production; its `Secrets.shaSecret` return is commented out.

`scripts/lint.sh` removes Windows download metadata sidecars whose basename ends in `:Zone.Identifier` before collecting files to lint. These files are local filesystem metadata, not project assets.

Generated output depends on project-wide filename rules. The watcher checks for duplicate basenames across `backend/`, `frontend/`, and `shared/` (including non-JS assets), and checks frontend/backend/dev JavaScript basenames against reserved words and browser/JavaScript globals. Preserve these constraints when adding or renaming files. HTML and Markdown basenames also need to be unique because they become runtime template keys.

Frontend generation also checks filename uniqueness on every build, rescanning current files. Image elements can use catalog references such as `src="Png.lavvo"` or `image.src = "Gif.reindeer"`; `AssetPaths.resolveImageSource()` finds the matching filename and extension in the generated image catalog and throws for missing or duplicate matches. Supported prefixes are `Png`, `Jpg`, `Jpeg`, and `Gif` (case insensitive); asset names are case sensitive. Ordinary URLs remain unchanged. Add the `stretch` attribute to an image to set its width and height to 100% of its containing box, filling that box even when the image aspect ratio changes. Global HTML injection resolves images initially and observes later `src` attribute changes, including property assignments. It observes each image once, preserving observation across removal/reinsertion. `HtmlObserverThing()` visits existing elements as well as newly added subtrees. `LoadAllImages()` preloads images and stores their path strings in separate plain `Png`, `Gif`, `Jpg`, and `Jpeg` objects so equal basenames with different extensions do not overwrite each other. Use these paths directly, such as `image.src = Png.lavvo`, `H.img(Gif.reindeer)`, or `setAttribute("src", Png.lavvo)`. Call `LoadImage(path)` when a native image object is needed for canvas drawing.

CSS is concatenated without resolving image catalog references. Use `bg-img="Gif.aurora"` on any HTML element to set its inline background image through the same catalog resolver used for image sources; ordinary URLs also work. Global HTML injection handles existing and newly inserted elements, and observes attribute additions, changes, and removals. Removing `bg-img` or setting it to an empty string clears the inline background image. Shared background sizing, positioning, and effects use the `[bg-img]` selector in `frontend/ui/css/bg-img.css`. Component template IDs are exposed on `html` before its paired JavaScript initializes; the entry point finishes loading image catalogs before mounting the hub.

`frontend/GlobalPopoverLogic.js` owns global popover target validation, option parsing, anchor allocation, custom open/close dispatch, and `on-hover-show="targetId"`/`on-hover-hide="targetId"` bindings. `InjectGlobalAttributeLogicToHtml.js` delegates popover targets to this helper while retaining generic dialog and ordinary-element show/hide routing. The target must be a `<pop-over>` component or carry the native `popover` attribute; invalid and missing targets throw explicit assertion errors when triggered. Hovering an `on-hover-show` element opens the target through the Popover API and anchors it to the hovered element; leaving closes it. An independent `on-hover-hide` target is hidden while the origin is hovered and shown again on leave, supporting ordinary elements and popovers. Multiple triggers can share one target, and the active trigger becomes its anchor. The Viking page's local `<pop-over>` component owns its active origin and `hover` or `click` mode through `open({ origin, mode, alwaysShow })` and `close({ origin, mode })`. A close request only succeeds for the origin and mode which opened it. It forwards `{ origin, popover }` to `onHoverShow[popoverId]` when shown and `onHoverHide[popoverId]` when a hover popover closes; click and general close callbacks remain separate.

Any element with an ID inside a registered `-page` can also use the page setup result's `onHoverShow` and `onHoverHide` maps without an extra HTML attribute. Global injection calls the matching callback with `{ origin }` on mouse enter and leave. Elements are observed once even if they are removed and reinserted.

`frontend/GlobalHoverLogic.js` owns these generic ID-based page hover callbacks. `InjectGlobalAttributeLogicToHtml.js` creates one hover helper and one `GlobalPopoverLogic` helper, then delegates each observed node to their `inject(node)` methods; keep their event binding and duplicate-observation guards out of the main injector.

Use the generic `on-click-show="targetId"` attribute for a click-opened auto popover; the same attribute detects dialogs and ordinary hidden elements automatically. Another auto popover or an outside click can replace an auto popover. Add the `alwaysShow` option after the ID, as in `on-click-show="targetId alwaysShow"`, to open a popover manually so other hover popovers can coexist with it; this option is rejected for non-popover targets. Switching an already-open component between these modes closes it, waits for its native close event, and reopens it from the new trigger. Close targets with the equally generic `on-click-hide="targetId"`; popover components can also use `dismiss()`. Both generic attributes without a value continue to show or hide the annotated element itself. The local component forwards `{ origin, popover }` to optional `onClick[targetId]` callbacks and `{ origin, popover, mode, alwaysShow }` to optional `onClose[targetId]` callbacks in the page setup result. Add `scrollable` and a constrained height when its content should scroll.

## Runtime and build workflows

Requires Node.js and npm. Install dependencies with `npm install`.

- `npm run dev` and `npm start` run `node watch.js`. The watcher regenerates `AllImports.js`, validates names, clears and rebuilds `dist/`, exports Aseprite assets, prepares the external bundle, serves the browser app on port `5050`, and starts the generated backend. On source changes it marks the backend unavailable, finishes the required generated outputs, then starts the backend; `/ping` reports readiness only after HTTP, SFU, and WebSocket startup. The browser waits for readiness before reconnecting. Backend code is transpiled into `transpiledBackend/`; the dev backend uses `DEVELOPMENT` configuration.
- Ctrl-C in the development watcher stops its backend/build children, watcher interval, and static server. The backend closes active FFmpeg, mediasoup, WebSocket, and HTTP resources before exiting.
- Start and manually test the project with `npm run dev`. For browser checks, always use the Chrome DevTools MCP backed by headless Chrome; this machine blocks regular Chrome windows from opening.
- Open `http://localhost:5050` for the browser app. The HTTP and WebSocket backend listens on port `3000`; the browser's development configuration connects there. SFU media transport also uses the configured mediasoup ports/network settings.
- `npm run startInspect` starts the watcher with Node inspector enabled.
- `node dev/GenerateFrontend.js PRODUCTION` generates production browser files in `dist/`; `PRODUCTION` or `DEVELOPMENT` must be passed because the transpiler substitutes the `ENVIRONMENT` marker.
- Use the Chrome DevTools MCP backed by headless Chrome for manual frontend checks; do not launch a regular Chrome window on this machine.
- When checking several tabs after a rebuild, reload each tab explicitly. The backend ID is stored in shared local storage; one tab can update it before another receives the reload message, leaving that other tab with cached modules.
- `node dev/ExportAseprite.js` exports `.aseprite` sources into generated browser assets under `dist/generatedAseprite/`. This requires Aseprite to be installed/configured; see `documentation/aseprite/`.
- `node start.js PRODUCTION` generates the backend into `transpiledBackend/` and launches it. In deployment, `Config` selects production HTTP, WebSocket, and mediasoup announce settings.
- `scripts/deploy_dist_to_netlify.sh` and `scripts/deploy_language_app.sh` generate a production frontend and deploy it with Netlify CLI. These publish externally; only run when deployment is explicitly intended. `scripts/deploy_server.sh` also runs remote SSH deployment operations.

`dist/`, `transpiledBackend/`, and `capacitor_setup/` are ignored generated output and may need to be generated before inspecting runtime output. The file scanner excludes `capacitor_setup/` so its copied browser assets do not participate in source filename or lazy-import discovery. `AllImports.js` is generated as a lazy-import table keyed by JS filename basename; the lazy loader expects a named export with that same name. The filename assertions enforce basename uniqueness in backend/frontend/shared, not uniqueness of arbitrary export names. The legacy root `test.js` is a standalone esbuild utility that expects a built `dist/`; there is no configured `npm test` script or standard test framework. `scripts/test.js` provisions a Capacitor Android project, removes/recreates `capacitor_setup/`, uses dependencies and machine-specific Android paths, and is not a unit-test command.

## Source transformation and module conventions

Read [documentation/coding_convention.md](documentation/coding_convention.md) before changing modules. The current conventions are unusual and enforced partly by custom generation:

- Use named exports for ordinary modules. Paired web component modules use matching hyphenated `.html` and `.js` basenames and `export default async ({ html }) => { ... }`; the host supplies the element with template IDs exposed on `html`. Mount these components with `H.create("component-name")`. Named exports should generally match their filename and remain globally unique.
- The project auto-inserts imports by scanning identifiers, including those in comments and strings. Naming a module in a comment can add an unintended import and create an initialization cycle; inspect generated imports when adding module references. Follow nearby files and avoid adding explicit imports in generated client code unless the specific module/pipeline requires them. `frontend/index.html` uses the `#root/` import map, and `package.json` maps `#root/*` to the repository root for Node.
- The frontend and backend generators share the same transpiler transformations for their respective JavaScript source files. These add inferred imports, class inheritance/constructor behavior, null checks, and control-flow rewrites. Shared source files are not otherwise transpiled. A change can fail or behave differently after transformation even if its source parses; inspect generated output or use the normal dev workflow when appropriate.
- The convention says to use tabs; follow nearby code. JavaScript lint rules are in `.eslintrc.json`, CSS rules in `stylelint.config.js`, and HTML formatting in `.prettierrc`.
- Keep class/module filenames in descriptive PascalCase where that matches the neighboring subsystem. Use globally unique basenames because automatic imports and filename assertions depend on them.
- HTML and Markdown files under `frontend/` are collected into runtime templates; hyphenated HTML files are treated as custom web components. Images/audio and Aseprite assets are cataloged during frontend generation, so names and locations can be significant.

Native prototype enhancements can use classes extending `shared/enhance/NativeEnhancer.js`. Pass the target prototype and optional `{ allowOverride, excludedMembers }` options to `super()`; instance methods, getters, and setters declared on the enhancer class are copied as non-enumerable descriptors. Instantiate enhancer classes with `new` from shared startup code. Any member already present anywhere on the target prototype chain requires an explicit name in the per-instance `allowOverride` option. The enhancer validates override and exclusion entries and all collisions before installing members; an override must match both an enhancer member and an existing target member. Use `excludedMembers` for runtime-specific members. Enhancer methods run with the native object as `this`, so do not use private class fields or `super` in copied members.

`HTMLElement.add(elements)` appends elements and returns a promise that waits for each appended element's optional `onAdd({ element, parent })` animation callback when the element is connected to the document. `HTMLElement.remove()` waits for the optional `onRemove({ element, parent })` callback while the element is connected, then removes it and resolves with the element; removing an already disconnected element skips the callback. These hooks are for add/remove animations; custom-component `onDomAdd` and `onDomRemove` remain lifecycle callbacks for setup, subscriptions, and cleanup. `Dom.remove(element)` delegates to the promise-aware element method.

`HTMLElement.playAndRemove(className, options)` wraps the enhanced `play()` method and removes the element after the animation ends, while preserving an optional `options.onEnd` callback. `FloatingHtml.add()` uses `e.playAndRemove("move-up")` after positioning its supplied element.

`FloatingHtml` is a class whose static block immediately creates a standalone `<overlay-fixed>` viewport overlay through `H.create()`. `FloatingHtml.add(popup, options)` appends any supplied DOM element at `DomMouse.x`/`DomMouse.y`, supplies fixed positioning, starts the `move-up` animation through `play()`, and removes the element from `play()`'s `onEnd` callback. Optional `x` and `y` override the current mouse position. Callers own the popup’s visual markup and styling and can supply arbitrary HTML converted with `.toHtml()`, such as the inline wood popup in `G.chopWood()`. `DomMouse` tracks viewport pointer coordinates for ordinary HTML interactions; the canvas `Mouse` tracker is reserved for world/canvas coordinates.

## Subsystem notes

- `D1`, `D2`, and `D3` export stable `DrawLayer(depth)` drawing instances and register their offscreen canvases with `Palette`; use them directly, such as `D1.rectangle(position, color)`. There are no `initD1`/`initD2`/`initD3` functions or `Palette.d1`/`Palette.d2`/`Palette.d3` surfaces. `Palette.initialize()` attaches the visible canvas once. `CanvasLayer` owns resizing, clearing, and filling for both visible and offscreen canvases. `Palette.render(run)` computes `Camera.transform` once, clears/transforms layers in one pass, runs drawing once, then restores/composites layers in a second pass with `finally` cleanup. Higher depths render first; lighting has depth `0` and renders last.
- Canvas world coordinates and mouse coordinates use CSS pixels. `CanvasLoop(activeThing, canvasParent = document.body)` places the main canvas in the requested DOM element; a body target makes it fixed to the viewport, while another target fills that element. `Palette.resize(width, height)` applies device pixel ratio and `renderScaleFactor` once to every canvas backing store; reducing render resolution does not change camera or mouse coordinates. `Camera.follow(position)` can be set before `CanvasLoop()` starts, and initialization preserves it. `Mouse.update()` updates input without drawing; the canvas loop draws its marker at `Mouse.position`. `SuperClass.showTags(draw)` receives a drawing instance from the canvas loop so shared base-class initialization does not depend on a browser drawing layer.
- `Snow` spawns around its supplied world position. Each airborne flake has a separate `altitude`; `Entity.y` remains its ground coordinate. Landing leaves a permanent, stationary deposit on `D2`, stored once per 8-pixel ground cell. Landed particles are removed from `Physics.objects` and `SuperClass.all`, including their position and center, while the ground deposits remain when the player moves.
- `H.Canvas(width=300, height=150)` returns `{ canvas, ctx }` without capturing a stream. `H.CanvasWithStream(width=300, height=150, frameRate=30)` returns `{ canvas, canvasStream, ctx }`. Use these helpers for DOM canvas creation; `OffscreenCanvas` layers remain separate. Livestream recording classes and their queue live in `frontend/apps/livestream/media/`, and the launcher test component lives in `frontend/apps/livestream/ui/test/`.
- `Fetch()` requires an explicit string `method`, checked by `Assert.string(method)`, with no default. `LowLevelHttpClient.get()` passes `"GET"` and `.post()` passes `"POST"`; omitting POST previously caused startup/token requests to hit the backend's file route and fail with HTTP 500.
- `Fetch()` returns `{ httpStatusCode, response }`, retries transport failures, and lets exceptions propagate. `LowLevelHttpClient.get()` and `.post()` forward to `_call(method, options)`, which owns token headers, POST body serialization, the local 200/500 status rules, and `{ ok, error, body }` results. It awaits body formatting so asynchronous parsing failures are caught along with request failures.
- Frontend network clients use `shared/Config.js` for HTTP/WebSocket URLs. Development points to `localhost:3000` and advertises mediasoup at `127.0.0.1`; production uses `krispetter.duckdns.org`. Local development does not depend on a Cloudflare tunnel.
- `Network`'s initial HTTP check runs from `frontend/index.js` after module imports resolve. Do not call `JsonHttpClient` from `Network`'s static initializer: `LowLevelHttpClient` depends back on `Network`, so doing so can hit the ESM temporal dead zone during startup.
- Frontend startup must finish `Token.init()` before calling `SocketClient.connect()`. Socket open and first-message handlers read `Token.decoded.internal.userId`, so starting both together can race against token initialization.
- Backend HTTP endpoints are registered by importing generated endpoint modules during `StartServer`; endpoint behavior and route conventions are implemented in `backend/http/` and `backend/http/server/`.
- WebSocket actions are registered by action name through `SocketServer.on`; coordinate action names and payloads with the corresponding client under `frontend/tools/network/`.
- Livestream and RTC code spans `frontend/apps/livestream/`, frontend multiplayer RTC clients, and `backend/rtc/`; changes may need coordinated client/server updates.
- `shared/chaos/ChaosMonkey.js` owns the valid chaos feature strings in the plain `ChaosMonkey.features` object. Each entry has an `enabled` boolean, initially `false`; toggle it directly, for example `ChaosMonkey.features.RETRY.enabled = true`. `assertValidFeature(feature)` throws for unknown strings. `maybe(feature, chance = 0.1)` and `maybeCrash(feature, chance = 0.1)` take the required feature first and optional chance second, with no message option. `delay({ feature, minMs, maxMs })` uses an options object. There is no separate enabled-feature set or `isEnabled()`, `enable()`, or `disable()` API. `Retry` accepts an optional feature and capped exponential backoff settings, so scoped chaos can exercise a specific retry path.
- Aseprite source files are stored below `frontend/`; the build exports tags, groups, layers, and tilemap metadata for browser loading. Generated source outputs are cached in `.cache/aseprite/` and copied into `dist/` for the browser build.
- `dist` static serving sets cross-origin isolation headers for `SharedArrayBuffer`/worker use. Preserve the equivalent headers in hosting configuration when changing deployment behavior.

## Checks and editing guidance

There is no standard automated test suite or `npm test` script. `scripts/check.sh` compares generated JS and bundle byte sizes; it is not a correctness test. Choose the smallest relevant verification for the change: run the dev watcher and inspect the browser/backend behavior, generate production output if changing generation, or run a focused utility. Do not assume `npm test` exists.

`node --test dev/tests/ControlFlowSyntaxChecks.js` runs focused control-flow checks for runtime/lint conversion, loop-header errors, parameter detection, generated execution, and ESLint fixes. It uses Node's built-in test runner and installed ESLint; no browser, server, or generated `AllImports.js` is required. The transformation helpers use direct imports so they can be tested before the watcher has started.

`node --test dev/tests/ImageSourceChecks.js` checks transpiled image-reference resolution, missing/duplicate references, ordinary URLs, loaded image catalogs, and filename-validation rescanning. It does not require a browser, server, or generated `AllImports.js`. Image catalogs are plain exported objects populated by the image loader; missing properties such as `Png.missing` return `undefined`. String references such as `"Png.missing"` still throw during source resolution.

`./scripts/lint.sh` is an in-place fixer, not a read-only check. It fixes source JavaScript, CSS, HTML, and ESLint globals in root files and the frontend/backend/shared/dev/scripts/prod/documentation folders. It excludes dependencies, generated output, `AllImports.js`, and `Secrets.js`. Equality fixes operate on parsed comparisons, preserving strings and comments. Run it from any working directory; dependencies must already be installed. JavaScript, CSS, and HTML checks run together and use content caches in ignored `.cache/lint/`. Whole-stage caches retain JavaScript/CSS diagnostic reports and successful HTML results, so unchanged runs skip loading the tools while still reporting existing errors. Adding, deleting, or editing source or configuration (including nested configuration) invalidates the relevant stage; dependency/package, Node version, and lint/conversion code changes invalidate all stages. JavaScript also has per-file caching for changed-stage runs. Only changed source/config files are written. Remaining errors produce a nonzero exit status. Review its diff carefully and avoid running it casually over unrelated work. `dev/UpdateEslint.js` regenerates globals without requiring `AllImports.js`; the lint runner supplies its existing file list to avoid rescanning source directories.

The lint runner returns exit status `0` when checks pass, `1` when lint errors remain, and `2` when it cannot complete (including configuration/tool failures or invalid arguments). `scripts/lint.sh` uses `exec` to pass the Node process status directly to its caller. A completed run can return `1` without throwing; cached lint errors also return `1`.

Before editing, inspect nearby modules and current Git changes. Do not overwrite unrelated user changes. Avoid running deployment, PR, remote SSH, port-killing, cleanup, or project-provisioning scripts unless that exact side effect is part of the requested task.
